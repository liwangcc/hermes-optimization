# 记忆功能的上游投稿计划

**现在只做本地准备。** 审阅从 [三份 Issue 草稿](ISSUES.md) 开始。逐份得到发布授权后发 Issue，先问维护者愿意看哪一段；明确回应后，再准备并请用户批准对应的独立 PR。不要当天一口气发七份，也不把「愿意审」理解成「同意合并」。[执行手册](RUNBOOK-HERMES.md) · [PR 正文](PR-DRAFT.md) · [证据](validation/EVIDENCE.md) · [Mac 复验](MAC-TEST.md)

## 1. 希望解决什么

- **记忆容量和维护**：能看出 `USER.md`、`MEMORY.md` 与 provider store 的用量、上限或不支持状态；后续再讨论用户主动触发的只读体检、提醒，以及目录和 `MEMORY.md` 共存时的提示。查看或体检不自动清理任何内容。
- **已有事实的向量索引**：支持从 Desktop/CLI 确定地启动任务并看到结果，不必反复对话等待隐式补索引。由 provider 决定实际任务、分批与续跑，核心不认识某个插件和模型。

## 3. 两边如何合作

- `hermes-optimization` 的 `holographic-semantic` 已实现相关可选接口，是参考使用方，向量存取由它的本机侧车负责。对外引用一个**可访问的提交 SHA**；没发布时不要假装链接可用。
- 上游 Holographic 是潜在的第二个使用方：先讨论 HOLO-1，无需等待主库；HOLO-2/3 不替换它自己的索引或要求安装侧车。字段语义、是否采纳和谁实现由插件维护者决定，未回复不算认可。
- 没有 provider 或 provider 不实现 hook 时，内置两层照常；新 Desktop 对旧后端不显示假 0，也不提供不可运行的任务。旧 Desktop 和旧的 web dashboard 不依赖新增字段。

## 4. 提交与证据纪律

| 阶段 | 门槛 |
|---|---|
| 本地候选 | 白名单提交适配器 + sidecar；另提交补丁、验证工具和文档。测试用独立安装、合成库，保留原始证据于本机。 |
| 发 Issue | 用户看过正文并同意，检查当前已有讨论；展示一两条代表性数字和范围。跨库引用只用真的 Issue/PR 编号。 |
| 发独立 PR | 维护者明确愿意审该段；按手册针对最新 base 验收，附完整结果、复现命令与限制，另获发布授权。 |
| 适配器发版 | 等对应 Hermes 接口有正式发布版本，再说明兼容范围、升级/重启侧车和回滚。候选不当作正式发版。 |

验证说明刻意分开三类：旧 Holographic 的真实模型「对话后回填」、早期 Desktop 的替身侧车 E2E、独立实装的真实 BGE-M3。**嵌入模型测试不等于 PR4 的真实生成模型体检**：进入 PR4 前另用 2–3 个真实生成模型记录解析成功率与失败样本。macOS 结果等朋友回执，不从 Windows 外推。
