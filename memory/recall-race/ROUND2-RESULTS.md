# 召回赛马第二轮：复核召回（先放宽找，再由交叉编码器挑）

2026-11-25。目的是让召回更准、更省 token，方法不设限。题目仍只用官方探针的公开题集，裁判台和基线 D0 沿用第一轮（[README.md](README.md)）。代码在 `round2/`，默认关闭的实现已写进日常版插件和侧车。

## 结论

1. **现状的问题不在「找不到」，在「挑不准」。** D0 注入的 1695 条事实里只有 27% 是答案，322 道闲聊题里 165 道被塞了事实；基座的实体流单独带进来 1 条答案、338 条非答案。而「基座结果 ∪ 余弦前 5 名」这个候选池已经装着 502/503 个答案（前 10 名是 503/503）。
2. **换一个会读两段文字的打分器来挑，准确度明显上去。** 用本机已有的 Qwen3-Reranker-0.6B 给每对「消息 × 候选事实」打分，再和「词法流是否命中」「是否余弦第一名」合成一个概率。规则在 dev 池上定好后冻结，在 test 池上只判了一次：

   | test 池（560 行，325 道有答案） | D0 | 复核召回 |
   |---|---:|---:|
   | 命中@5 | 304 | 307 |
   | 第一条就是答案 | 286 | 307 |
   | 展示的事实 / 其中非答案 | 1181 / 860 | 733 / 411（−52%） |
   | 展示精度 | 27% | 44% |
   | 噪声行 / 混淆行 | 130 / 34 | 88 / 24 |
   | 救回 / 丢失（题） | — | 4 / 1 |

3. **库变大后差距更大。** 把同一语言的几个库并成一个（262–298 条事实），让官方插件在大库上真跑一遍基座：D0 精度掉到 19%，复核召回命中@5 262 → 272，非答案 1239 → 595，噪声行 211 → 147，混淆行 44 → 28。
4. **指针不能砍，但可以从「全量静态目录」换成「每轮最多 4 条动态指针」。** 自动召回没展示的 38 个答案里 37 个出现在指针里；每轮约 28 token（静态目录是 1546，大库是 2976 且已被截断）。原因见下面「任务型消息」一节：需要某条约定但不直接问的消息，新旧自动召回都很差，只能靠指针。
5. **没有过完整四条门禁。** 全题集救回 10 题、丢 2 题（p = 0.039），噪声和混淆都降，但丢了 4 个 D0 原有的答案，其中 3 个是「孩子们 / 父母」这类一问多人的第二个答案。只加不删的变体不丢答案、p = 0.002，但噪声行和混淆行各多 1 行。
6. **代价是一个要 GPU 的小模型。** 每条消息多约 0.2 秒、1.3 GB 显存（RTX 4060 笔记本）。纯 CPU 上每条消息约 15 秒，不可用。

## 做法

每条消息只多调一次侧车（`/judge`）：

1. **候选**：基座本轮要展示的事实，加上余弦最近的 10 条。
2. **打分**：交叉编码器把消息和事实（正文加关键词）放在一起读，同一批里读两遍：
   - 严格读法（「回复这条消息需不需要这条笔记」）决定全文展示什么；
   - 通用读法（模型自带的检索提示语）只用来给指针排序。
3. **全文展示**：`p = sigmoid(0.55·严格分 + 0.56·词法流命中 + 2.35·余弦第一名 − 2.18)`。
   - 现状本来会展示的事实，`p ≥ 0.03` 才保留；
   - 其余候选 `p ≥ 0.2` 才加入，并且要过基座原有的人名、可召回和重复窗口检查。
4. **指针**：没展示的候选里，通用读法分数最高的 2 条（不低于 −5），再加余弦最近的 2 条（不低于 0.40），以 `#编号=标签` 列在块后面。已展示的事实里有 `p ≥ 0.9` 的，认为已经答上，不列指针。

三个信号各自会错在不同地方：词法流把同名的人的事实全带进来，余弦分不清「像」和「能回答」，小模型会把「安德烈多久跑一次步」和「安德烈每月值一次夜班」配上。合在一起才稳。

| | 命中@5 | 第一条是答案 | 找到的答案 | 展示 / 非答案 | 精度 | 噪声行 | 混淆行 | 救回 / 丢失 |

### 指针和 token（all7，每轮平均，approx_tokens）

| | 召回块 | 目录 / 指针 | 合计 | 没展示的答案里指针可见 |
|---|---:|---:|---:|---|
| D0 + 静态目录（标签 30） | 46 | 1546（静态，可缓存） | 1593 | 30 / 38（同一批答案，另 8 个因目录超预算被截掉） |
| 复核召回 + 动态指针 | 32 | 28（每轮现算） | 60 | 37 / 38 |

- 按缓存读价 0.1 折算，静态目录每轮约 155，合计约 201；动态这边是 60。
- 指针只在 393 / 818 轮出现，平均 1.4 行。
- 动态指针跟着用户消息进对话历史，会随轮数累积。一个会话超过约 50 轮不压缩时，累积量才接近一份静态目录。
- 这批题的事实都很短（十几个 token）。真实库平均 355 字一条，非答案减半省下的 token 会比这里多得多，没有实测。

### 任务型消息（风险探针）

官方题集全是直接问事实，规则也是在这种题上定的。另写了 24 条任务型消息和 12 条不需要任何事实的消息（`round2/task_probe.json`，在看到任何分数之前写好），库是 synthetic_zh 的 30 条项目约定。例如「给商品列表加一个按名称查找的功能」需要「搜索用 Elasticsearch」。

| | 需要的约定：全文展示 | 再加指针里的 | 展示的无关事实 | 12 条无需求消息：有全文 / 指针行数 |
|---|---:|---:|---:|---|
| D0 | 8 / 25 | — | 8 | 1 / — |
| 复核召回 | 5 / 25 | 17 / 25 | 4 | 0 / 21 |

- 新旧自动召回在这类消息上都差。打分器的绝对分数是负的（它判断的是「能不能回答」），但**排序是对的**：通用读法把需要的约定排在全库第一的有 16 / 25，前三 21 / 25；余弦是 7 / 25 和 14 / 25。所以指针用通用读法排序。
- 这类需求正是指针的主要用途，所以指针保留。全量静态目录能列出 25 / 25，但混在全部条目里，模型会不会去看没有测。
- 这组题是我自己写、自己标的，只有 24 条，当风险提示看，不当结论。

### 打分器本身

| dev 池候选对（2713 对，156 个答案） | 区分度（AUC） | 留下 50 条非答案时保住的答案 |
|---|---:|---:|
| 余弦 | 0.900 | 82 |
| 交叉编码器，只读正文 | 0.934 | — |
| 交叉编码器，正文加关键词 | 0.969 | 120 |
| 加上词法流、余弦第一名（交叉验证） | 0.977 | 136 |

- 事实后面拼上关键词再给打分器读，比只读正文好一截。
- 把提示语写得更长更细（两版）反而变差，就用最初那条。
- 只用打分器一个分数、一条线来挑（R2_one_bar）会丢掉 D0 靠词法或余弦找到的答案，所以对「现状会展示的」放低线、对「新加的」抬高线。

### 插件实测（端到端）

`round2/native_check.py`：官方插件建库，侧车作为子进程带 BGE-M3 和打分器，日常版包装器打开 `semantic_judge`，每题新会话。household、contrast、synthetic_zh 共 7 个库、618 行，和离线规则逐行比：

| | 结果 |
|---|---|
| 展示的事实相同 | 604 / 618（顺序也相同 591） |
| 指针相同 | 592 / 618 |
| 汇总（命中@5 / 非答案 / 噪声行 / 混淆行） | 离线 273 / 524 / 129 / 31，插件 273 / 522 / 128 / 31 |
| prefetch 耗时 | P50 246 ms，P95 304 ms，最慢 398 ms（不开时 P50 约 41 ms） |

不同的 14 行全部是某条事实正好压在线上（`p` 在 0.03 或 0.2 附近）或余弦前两名几乎并列。原因是打分器用 bf16、一批里的文本长短不同会让分数浮动：平均 0.07、最大 0.44。

## 没有成立或没做的

- **只按打分器给指针排序**：漏掉的答案正是打分器否掉的，所以必须有一路不依赖它（余弦）。
- **指针规则不是留出结果**：第一版（余弦前 3 名）跑过 test 之后才换成现在这版，依据是 dev 和任务探针，但我已经看过 test 上的覆盖数。全文展示的规则没有动过。
- **CPU**：i7-12650H 四线程每条消息中位数 15 秒。插件里判失败后 60 秒内不再问打分器，退回现在的做法。
- **真模型在环**：指针换成每轮 2–4 条后，模型会不会 get、会不会多余地 get，没有测。这要用 11-24 那套 `behavior/run_denoise.py` 和你的接口。
- **真实库**：在项目外，没有跑。`round2/real_ab.py` 给一份库副本和标注题就能跑，只输出计数（命令见下）。
- **多轮对话**：追问、代词指代、重复窗口都没测，题集每题都是新会话。
- **只测了 BGE-M3 加 Qwen3-Reranker-0.6B**，库最大 298 条。「余弦第一名」这个信号只用名次，不依赖模型的分数刻度，但系数是在这一对模型上拟合的。
- test 池里的 contrast 和 multi 在项目更早的轮次里用过，不是全新的题。本轮规则的设计没有碰它们。
- 题集里的闲聊大多是带人名的招呼（「嘿，奥莉娅！」），打分器对这类只给到 0 分上下，压不干净，噪声行还剩 129 / 358。

## 等你决定

1. **要不要在日常版上试开。** 我的建议是试：先在真实库副本上跑 `real_ab.py` 看计数，再开。
2. **静态目录关不关。** 建议先别关，等真模型测过「动态指针对全量目录」再定。
3. **丢 4 个答案能不能接受。** 不能的话用只加不删的变体（`KEEP` 设成 0），代价是降噪那一半没有了。

## 复现

在 `memory/recall-race/` 下运行，Python 3.11、PyTorch 2.11（CUDA）、transformers 5.8.1，模型在 `vendor/models/`。

```
python -X utf8 -B round2/score_pool.py            # 给 8389 对候选打分（6 组，约 9 分钟）
python -X utf8 -B round2/sweep.py                 # dev：各分数的区分度和单线扫描
python -X utf8 -B round2/combine.py               # dev：交叉验证各种信号组合
python -X utf8 -B round2/combine.py --freeze judge+words+top1     # 写 model.json
python -X utf8 -B round2/final.py                 # 冻结规则和拆分变体过裁判台，写 results/R2_*.json
python -X utf8 -B round2/build_big.py && python -X utf8 -B round2/big_eval.py     # 合并大库
python -X utf8 -B round2/task_eval.py             # 任务型探针
python -X utf8 -B round2/native_check.py          # 插件端到端对离线规则
python -X utf8 -B round2/real_ab.py --store <库副本> --queries <标注题> --tau 0.55 --cap 9   # 你自己的库，只出计数
```

`scores*.json`、`big_rows.json`、`sub/` 都可以重新生成。`final.py` 每跑一次会在 `runs.log` 里记一行。
