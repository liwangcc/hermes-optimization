# 召回赛马第一轮：结果

> 第二轮（2026-11-25，换打分器来挑候选、动态指针）见 [ROUND2-RESULTS.md](ROUND2-RESULTS.md)。

2026-11-23。按 `recall-race-brief.md` 并行跑了三条路线。题目只用官方探针的公开题集。裁判台、基线和统计由主窗口负责，三条路线各由一个子代理实现（haiku）。裁判台的说明见 [README.md](README.md)，全部选手的原始表格见 [RESULTS-TABLES.md](RESULTS-TABLES.md)，每个选手的成绩和失败清单在 `results/<名字>.json`。

## 结论

决策权在用户。下面是证据支持的判断，所有选手的成绩都在后面的表里，不只列胜者。

1. **路线 A（关键词加分）没有效果。** 把它的两个改动拆开分别测（主窗口补测），关键词加分本身只让 all7 命中 ±0 到 −2、噪声 −1 到 −5，均不显著。它表面上的变化来自另一个结构改动：第一名已经展示过时改追加第二名。这个改动让混淆从 53 升到 59。加分无效的原因：侧车的向量文字本来就是「正文 + 关键词」，再按关键词加分等于把同一个信号算两遍。
2. **路线 C（换序）没有效果。** 换成「关键词 + 正文」后 all7 命中 425 → 424，混淆 +1，丢 2 个目标。现在的「正文 + 关键词」是测过的拼法里最好的：去掉关键词、在 dev 上把追加数调到和 D0 相同后，all7 少中 9 题。串行硬筛的粗筛宽到前 10 时几乎等于 D0（噪声 −3，属于 cleaner），收窄到前 3 就开始丢题。
3. **路线 B（catalog）有效的做法是「静态、标签压短」，不是按题裁剪。**
   - 只改配置 `catalog_label_tokens`，从 30 改成 12：单库每轮 1547 → 1403 token（−9%），漏掉的目标里指针可见从 37 升到 44（全部可见），catalog 仍然每轮相同、可缓存。代价是 2/44 的标签和别的事实重复。
   - 改成 8：单库 −33%（1036 token）；大库也能装进 3000 预算，可见从 16 升到 44。代价是 8/44 的标签重复：长事实只剩关键词，人名丢了，几个人的生日长得一样。
   - 改代码，按事实开头截到 12 token（路线 B 的 C2）：单库 1406 token，44/44 可见，零重复，「看得见且排前十」39/44。但在大库上超出预算 23%。
   - 按题动态生成的方案（C1、大库上的 C3、C4）都进不了 prompt cache。C4 每轮只有 280 token，但它用的是同一个会漏的向量机制，漏掉 6/44，违反 brief 的 B1；按缓存读价 0.1 折算，它比 C0 还贵（280 对 155）。
4. **没有一个方案过完整的四条门禁。** 召回一侧没有「显著救回、又不加噪声和混淆」的做法。能多救回的变体（A_soft_b 救回 7、丢 0、p = 0.016）同时多出 28 行噪声、15 行混淆，本质上和降低阈值一样，是拿污染换召回。

## 基线和裁判台

- 形状是日常版：基座关向量，只走词法，事实带官方冻结的关键词；侧车按 `cos(正文 + " " + tags)` 追加最近的 1 条（阈值 0.55）。catalog 每条事实一行 `#id=标签`，3000 approx-token 预算。
- D0（现状日常版）在 all7 上：命中@5 425/460，噪声行 194，混淆行 53，侧车追加 106 条，其中 34 条是目标（精度 0.32）。只用基座时是 393/460、噪声 152。
- 题池：dev（household dev 加 synthetic_zh）用来调参，test（multi 8 种语言、contrast 英俄中、household test）用来判定。调用记录：A 调参 305 次、B 10 次、C 64 次，全部在 dev 上；test 只在 `--final` 时出现（A 8 次、B 17 次、C 10 次）。三条路线的代码都没有读标签文件。
- 自检：在官方探针的 818 行上，重算出的混淆和噪声与探针自己的字段逐行一致。

## catalog（all7 池，同一批 44 个漏掉的目标做分母）

- 按缓存读价折算（r = 缓存读价 / 正常输入价，例如 0.1）：静态方案每轮的有效成本是 token × r，动态方案按 token × 1。r = 0.1 时 C0 约 155、标签 12 约 140、标签 8 约 104，C4 是 280。动态 catalog 绝不能放进 system prompt：它每轮都变，会让后面的工具定义和对话历史的缓存全部失效。
- C4 漏掉的 6 个目标：`contrast_zh p3q0:denis_car`、household en 的 `q035:pavel_fish`、`q066:pavel_tv`、`q070:dima_games`，以及 household zh 的 `q035:pavel_fish`、`q070:dima_games`。C0 在单库上漏掉的 7 个全在 household ru：俄文按 approx_tokens 计更贵，这个库超出预算，最旧的事实被截掉。
- 混合方案（静态加动态差点被召回的指针）在这里测不出收益：静态部分已经列出全部指针，动态部分只是把同一批指针用全标签再列一遍，只看得到 token 代价。

## 主窗口补测的四项

1. **拆开路线 A**（`routes/M/a_split.py`，用 A 在 dev 上定好的参数，不重新调）：结论见上面第 1 条。
2. **只改配置能不能拿到 C2 的收益**（`routes/M/cfg_label.py`）：标签 12 的单库结果和 C2 几乎一样，不用改代码；8 更省，但有重复标签。
3. **重复标签**（`routes/M/dup_labels.py`）：余弦代理指标遇到并列不扣分，会高估关键词标签。8 token 的配置有 6.7% 的行撞标签。
4. **「主实体: 关键词」标签**（`routes/M/entity_label.py`）：12 和 10 token 时零重复，排前十的数和配置 12 相近；8 token 时实体名吃掉预算，排前十掉到 30。8 token 这一档没有找到两头都占的写法。

## brief 里的设计遗漏和事实出入

1. **prompt cache 没有考虑。** catalog 在 system prompt 里，每轮相同，插件代码特意让新事实追加在末尾，好命中缓存。「每轮三四千 token」在支持缓存的服务上按缓存读价计费。按本轮题目排序或裁剪（C1、C3、C4）就进不了缓存。
2. 上限是 `catalog_max_tokens: 3000`（approx_tokens 估算），不是 `CATALOG_CHARS = 6000` 字符。
3. bge-m3 用的是 CLS pooling（`vendor/models/bge-m3/1_Pooling/config.json`），不是 mean pooling。路线 C1「影响小」的理由不成立，实测结果是略差。
4. 官方题集上，D0 前五只漏 35 题，不在输出里的目标只有 44 个，召回一侧的空间本来就小。侧车追加的精度只有 0.32，主要的空间在降噪，而降噪的路线（加分、换序）都没做到。
5. 侧车追加的事实在基座已有 5 条时排在第 6、7 位，官方的命中@5 不算它们。表里另给了「任意位置」的命中。
6. B1 量的是「指针看得见」，不是「模型会去 get、并且 get 对」。后者要真模型在环里测。
7. 官方题集的事实没有 trust 差别，「高 trust 详细展示」测不了。

## 没测的和限制

- multi 只用了冻结关键词覆盖的 8 种语言（官方七集是 18 种）。
- D0 是按日常版 `_add_semantic` 的逻辑离线复现的，不是装上插件和侧车端到端跑出来的。基座部分是官方探针实跑。
- big 探针的召回沿用单库结果，大库里的召回只会更差，所以 B1 那一侧偏乐观。
- dev 池里只有 18 个漏掉的目标，catalog 调参的噪声大。路线 B 的 C2 取 12 token 是看完网格才定的规则（它自己写明了）。
- token 用的是插件的 approx_tokens。按 cl100k 计会高约 15% 到 50%（多语言文字在 cl100k 上偏贵；标签越短、非英文越多，高得越多），方案之间的排序不变，但标签 8 的节省按 cl100k 算会小一些（单库 1967 → 1479，−25%）。
